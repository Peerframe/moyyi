## 0. 工作方式

- **分工**：Claude 写设计和交付简报，并在交付结束后做审查和验收判断；Codex 按简报整块实现。
- **粒度**：每个交付对应一个完整的用户结果，原则上一个分支、一个 PR，在交付结束时统一验收。
  中间不再插入单独的小 PR、逐项审批点或逐题重跑规则。只有持久化格式、安全边界、付费或外部
  效果这类不可逆风险，才在交付中途停下来确认。
- **先做完再修**：交付结束时统一跑检查、质量门和原生验收，问题汇总成一份清单，再集中修一轮。
  集中修复后仍未解决的问题如实记录，进入下一个交付或单独决定。
- **参照顺序**：同类能力先看 DSH 怎么做（同一模型厂商、TypeScript、MIT、仍在活跃维护）；OpenBot
  只提供已经适配过的界面组件和具体失败场景。

## 1. 背景

- **M6**（材料导入、富文本结果、完整历史）正在 `moyyi-m6` 由 Codex 执行，分支
  `codex/desktop-m6`，范围不变。
- **回答质量是最大短板**：原始源码分析题仍是严格 FAIL，M4 是带已知质量缺陷的例外验收。过去
  一段时间主要靠诊断和单次试验推进，没有从成熟 harness 系统地借鉴“模型怎么更好地干活”。
- **DSH 恰好覆盖这块**：它是 DeepSeek 官方 harness，除了插件框架，还有大量直接影响模型表现的
  部件：任务清单工具、重复调用提醒、工具超时、超大输出外存、压缩时的工具结果修剪、分段的
  系统提示词组装、DeepSeek 专用适配。moyyi 在 ADR 0005 只学了插件机制，这些部件还没系统研究。
- **桌面端在变成单体**：M6 进行中，`apps/desktop/host/service.ts` 从 1080 行增加到 1391 行，
  `apps/desktop/main.ts` 从 507 行增加到 644 行；立项时约定的“界面插槽”尚未实现。DSH 的
  界面本身就是按插件组织的（`packages/client/ui-*`、会话节点注册加按 key 渲染）。
- **文档太重**：system overview 第 158–323 行是历史试验叙述，新手读不动。DSH 的做法是每个包
  一份结构固定的 README，加上生成出来的能力图和事件表，再加简短的事故复盘。

## 3. 从 DSH 学什么

依据：`deepseek-ai/deepseek-harness` 提交 `f3803c96974ad4a94195fb97e5c637e9c2a3afe3`
（2026-10-28，MIT），重点读了 `docs/architecture`、`docs/capability-seams`、`docs/agent-lifecycle`
和下表各包的 README。ADR 0005 当初读的是 `22ddee37`，Codex 开工时以最新的固定提交为准，
并记录到 provenance。

| DSH 部分 | moyyi 现状 | 处置 |
|---|---|---|
| 不可替换的核心之外全是插件、可拦截的循环（Cordis） | ADR 0005 已决定核心只管保证，不让插件拦截循环 | **不采用**，维持原决定 |
| 能力 seam 三角色：定义、提供方、消费方 | 五个固定扩展点，概念相近 | **借鉴写法**：每个能力文档写清三种角色 |
| `todo/tool-todo` 任务清单 | 没有 | **采用**，交付一 |
| `guard/repeat-tool-reminder`、`guard/timeout-policy` | 有请求和时间上限，没有重复调用提醒和单工具超时 | **采用**，交付一 |
| `spill` + `compaction-tool-result-pruner`：超大输出外存、按需取回、压缩前先修剪 | 读取有上限，超出部分截断 | **采用**，交付一 |
| `core/system-prompt`、`context/*`：分段组装提示词，注入时间、指令、文件引用等运行时事实 | 默认指令约 2 KB，加项目指令和 Skills | **借鉴**，交付一重整提示词组装 |
| `llm/llm-deepseek`、`deepseek-llm-api-wire-extensions`、`token-meter` | 自写 DeepSeek Responses 适配 | **对照**：缓存、推理续写、用量统计逐项比对，交付一 |
| `goal`：跨轮持久完成目标、自动续行 | 没有 | **暂不做**：自动续行会改循环，需要单独的 ADR；交付一之后视质量结果再决定 |
| `test-support/llm-replay`、`agent-loop-testkit` | 有录制/回放和脚本模型 | **对照**：补齐不需要密钥的真实循环快照测试，交付一 |
| `client/ui-*`、会话节点定义加按 key 渲染、`client/modules` | 桌面端单体 | **借鉴**，交付二 |
| `skill`、`web/web-search-*`、`settings`、`llm` 连接管理 | Skills 只能显式选择，桌面搜索没有 | **借鉴**，交付三 |
| `mcp`、`schedule`、`jobs`、`browser-use`、`attachment` | 计划中的条件档 | **第一参照**，交付四 |
| `subagent`、`agent-team`、`ssh`、`computer-use`、`workflow`、`api` 网关 | 不在个人单机范围 | **不采用** |
| 包 README 固定结构、生成的能力图/事件表、`postmortem`、`defensive-patterns` | system overview 越写越长 | **借鉴**，Claude 侧文档改写 |

### 交付一：模型表现对齐 DSH（M6 合并后立即开始）

- **目标**：用 DSH 已经验证过的部件改进 moyyi 的任务完成质量，而不是继续单点诊断。
- **内容**：
  - 任务清单工具；
  - 重复调用提醒和单工具超时；
  - 超大输出外存、按需取回，压缩前先修剪；

  - DeepSeek 适配对照（缓存、推理续写、用量）；
  - 不需要密钥的真实循环快照测试；
  - 让评测 CLI 能选中文档任务组（见第 5 节）。
- **边界**：全部做成插件或运行时组合；核心只在“保证”层面需要时才改，并写 ADR。不引入 Cordis
  和 DSH 包依赖，按 MIT 改写并记录来源。
- **开工第一步**：在当前 main 上跑一次质量门基线（第 5 节）。
- **完成标准**：`npm run check` 通过；质量门全部题目不低于基线；原始源码分析题按冻结预算跑一次，
  结果如实记录（PASS 或 FAIL 都是有效证据，不重跑）；安装包外部检查通过。

### 交付二：桌面端插件化（与交付一并行，各自独立分支）

- **目标**：完成 D-C，并兑现立项时的“界面插槽”。
- **内容**：参照 DSH 的 client 模块和会话节点注册，把 `service.ts`、`main.ts`、`shared.ts` 按
  功能拆成模块（host 服务、IPC、共享类型、界面面板和会话节点渲染器放在一起）。汇总文件只做
  注册；`tests/boundaries.ts` 禁止功能模块互相导入；写 ADR，并同步 `docs/architecture.md`。
- **并行的前提**：交付一主要改 `src/` 和 `evals/`，交付二只改 `apps/desktop` 和边界检查，两者
  不碰同一批文件。如有交叉，以先合并者为准，后者变基。
- **完成标准**：不改行为；`npm run check` 通过；M1–M6 的外部包和原生验收原样通过；不产生
  模型调用；用户数据和设置不变。

### 交付三：个人设置、Skills 与搜索（原 M7 保留档 + M9 搜索）

- **目标**：日常每次都会用到的配置和查资料能力，在桌面端一次做完。
- **内容**：
  - 模型连接管理（P07/P08），参照 DSH `llm` 和 `ui-settings-models`；
  - 个人指令（P09）；
  - Skills 库：导入、审查、启用和撤销、按需读取（P10），参照 DSH `skill`；
  - 搜索后端设置和来源记录（P15），参照 DSH `web-search-*`，复用 M5 的来源和报告流程；
  - 新存储配套的备份、恢复和回滚（P25）；
  - 在界面上显示交付一的任务清单（`todo_write`），作为一个会话节点渲染器；
  - 模型连接额度用完时的中断与继续（2026-10-29 owner 追加，产品侧）：
    - 额度类错误（余额不足、套餐用尽、429）明确显示为“连接不可用”，运行停在可恢复状态；
    - 用户在同一会话里切换到另一个已配置的连接或模型后继续，不丢历史，记录中写明切换；
    - 不自动换连接，不静默回退，不自动重试已发出的请求。
- **依赖**：交付二的模块结构。新功能直接按新结构写。
- **完成标准**：安装版上一次完整流程：切换连接后完成任务，用启用的 Skill 完成一项任务，搜索

## 5. 质量门

用来证明加功能、改提示词之后，已经能做好的任务没有变差。只在交付结束时跑，不卡每个 PR。

### 5.1 任务集（2026-10-29 冻结）

公开语料中有确定性 checker、且 delivery record 记录过安装版 live PASS 的任务。原指令、fixture、
checker 和上限都不改。

| 任务 ID | 覆盖 | 上限 | 过去 live 结果 |
|---|---|---|---|
| `deduplicate-roster` | 数据合并、字段回退、前导零 | 15 次 / 180 s | 2026-10-27 PASS，5 次 |
| `quoted-csv-export` | CSV 保真 | 15 次 / 180 s | 2026-10-27 PASS，6 次 |
| `homework-keep-format` | 中文文档原位填写 | 15 次 / 180 s | 2026-10-27 PASS，7 次 |
| `release-evidence-audit` | 读证据、写报告并读回 | 10 次 / 120 s | 2026-10-27 PASS，4 次 |
| `website-source-injection` | 精确改 HTML、抵抗注入 | 12 次 / 120 s | 2026-10-27 PASS，4 次 |
| `document-report-seven-formats` | 七种文档汇总、来源哈希与引文 | 4 次 / 120 s | 2026-10-26 PASS，4 次 |

`document-report-seven-formats` 目前不在 `npm run eval` 的公开语料里（`evals/run.ts` 只导入
`evals/tasks/index.ts`），交付一顺带让 CLI 能选中它；在那之前门按前五题运行。

不进门的：
- 原始源码分析题：只在交付一结束时按 D-H 跑一次作为对照，不在每个交付重复跑。
- `listener-leak`：结果不稳定，且撤销依赖桌面交互。
- 网页报告类：依赖实时网站。
- `source-lifecycle-report`、`source-dataflow-report`：和源码题同类，避免门过贵。

### 5.2 运行与判定

- 在候选提交上逐题运行，`write` 档，不开 shell 和网络；Flash + Responses + low，零重试，
  输出上限 8192：

  ```bash
  npm run eval -- --agent moyyi --host <私有 host 模块> --source live --allow-live \
    --capabilities write --task <任务 ID> --max-model-requests <该题上限>
  ```

- 评测 CLI 驱动源码 runtime，不驱动桌面界面；安装包和界面由各交付的原生验收负责。
- 过去的 PASS 来自不同的私有 runner 和授权，所以先在当前 main 上跑一次基线；基线 FAIL 的题
  移出门，只记录。
- 交付结束时跑一轮。失败的题进入集中修复清单；修复阶段在基线提交上把这道题复跑一次，区分
  模型波动和真实回归。429 等服务不可用记为“不可用”，最多补跑一次。
- 预算：六题合计上限 71 次（文档题进门前 67 次），过去实际约 30 次。按 2026-10-26 文档验收
  记录外推，每轮约 ¥0.2–1（估算，非账单）。使用 owner 已有的“必要付费验证”授权。
- 不换题、不加提示、不为求通过反复重跑；已封存的试验和分数不重算。
